# feat: Run a pending hosted tenant from Firestore          ✅ COMPLETED — 2026-09-12

## Problem

Hosted Hisab ([spec 001](../../specs/001-hosted-portal.md), [brainstorm](../../brainstorm/hosted-portal.md), parent [#1](https://github.com/mhmzdev/hisab-whatsapp/issues/1)) needs a process that turns a Firestore tenant document into a running, isolated Hisab worker. Today `landing/` ([#3](https://github.com/mhmzdev/hisab-whatsapp/issues/3), done) is a static shell with no backend — `NONCE` is a display constant, there is no Firestore, no runner, no decryption. [#4](https://github.com/mhmzdev/hisab-whatsapp/issues/4) is the keystone: [#7](https://github.com/mhmzdev/hisab-whatsapp/issues/7) (connect a portal user), [#6](https://github.com/mhmzdev/hisab-whatsapp/issues/6) (quota) and [#8](https://github.com/mhmzdev/hisab-whatsapp/issues/8) (export) are all blocked on it, directly or transitively. Blocked by: nothing (issue body confirms).

This plan builds the reconciler and worker lifecycle only. It does **not** implement nonce matching, the welcome message, quota, revoke UI, or `export-ledger` — those are #7, #6, #5, #8. It also does not implement Firestore security rules for portal client writes (also #7's surface); the runner uses the privileged Admin SDK, which bypasses rules entirely.

**Decided fork (confirmed with Hamza before writing this plan):** the spec locks the encryption scheme (portal encrypts the WhatsApp key client-side with a runner-held public key; Firestore stores only ciphertext; the runner alone holds the private key) but not where that keypair comes from, how it reaches the container, or how it rotates. Decision: the runner's keypair is generated once by a small script and held as an environment-variable secret exactly like `WHATSAPP_TOKEN`/`OPENROUTER_API_KEY` — `.env`, never committed. Rotation for this MVP (local/dev only, no production per spec's Environments section) is manual: regenerate, redeploy, and any ciphertext sealed under the retired public key can no longer be decrypted — that tenant must resubmit its key through the portal. This follows the brainstorm's own phrase ("a secret that exists only on the VPS," `docs/brainstorm/hosted-portal.md:63`) and this repo's existing secrets convention (`hisab/config.py:27-31`); it is not a new scheme.

## Approach

**New `runner/` package, independent of `hisab/`.** Reuses `hisab.loop` unchanged as the per-tenant worker: the runner writes a per-tenant config YAML and launches `python -m hisab.loop --config <path>` as a subprocess with a per-tenant environment (`WHATSAPP_TOKEN` decrypted from that tenant's ciphertext; `OPENROUTER_API_KEY`/`GEMINI_API_KEY` inherited from the runner's own environment, i.e. global, never tenant-supplied). This is the smallest change that satisfies "one worker process per tenant" (spec, "Tenancy on the VPS") without touching `hisab/`'s tool-calling core.

**One exception in `hisab/`:** a `pending` config flag (`hisab/config.py` DEFAULTS gets `"pending": False`) that `hisab/loop.py:_handle_wa` checks before doing anything else — when true, the inbound is recorded to the store (so a later feature can inspect it) and the function returns; `self.handle(...)` and `wa.send(...)` are never called. This is a strict superset of "sends nothing before it receives an inbound message" (it sends nothing, ever, while pending) and is deliberately conservative: #7 owns detecting the `verify <nonce>` command and flipping Firestore status, at which point this runner's reconciler restarts that tenant's worker without the flag. Self-host is unaffected — `pending` is absent from every existing config file and defaults false.

**Tenant paths are opaque.** `build_tenant_config(uid, tenant_doc, runner_cfg)` sets `ledger.path = f"{runner_cfg['vault_root']}/{uid}"` and `state.path = f"{runner_cfg['data_root']}/{uid}"` using only the Firestore document id (the Firebase `uid`) — never `agentName`, `creatorId`, or a phone number. `model`/`transcription` are always copied verbatim from `runner_cfg` (the runner's own shared config, sourced the same way `config.yaml`/`config-dev.yaml` are today); the tenant document schema (`docs/specs/001-hosted-portal.md:81` — agentName, keyCiphertext, creatorId, status, language, plan, timestamps, activity) has no model-credential field to begin with, so this is enforced by construction, and a fixture test asserts it explicitly.

**Decryption.** `runner/crypto.py` wraps PyNaCl's `SealedBox` (the "sealed-box/envelope encryption" the brainstorm already names, `docs/brainstorm/hosted-portal.md:43`): `generate_keypair()` for the one-time setup script, `decrypt(ciphertext_b64, private_key_b64) -> str` raising a typed `CryptoError` on failure (wrong key, corrupt ciphertext) rather than an opaque exception. `runner/keygen.py` (`python -m runner.keygen`) prints a fresh base64 keypair and instructions: the private half goes in the runner's `.env` as `RUNNER_PRIVATE_KEY`; the public half is a build-time constant the portal embeds (safe — it's public).

**Idempotent reconciliation.** `runner/reconcile.py` takes the *whole current tenant collection* (a Firestore `on_snapshot` callback naturally hands you this) and a `WorkerManager` (`runner/workers.py`). For each tenant doc: `status in ("pending", "connected")` → compute a `state_hash` over exactly the fields that should cause a restart (decrypted token, the `pending` flag, the model/transcription block, the ledger template) and call `manager.ensure_running(uid, config_path, env, state_hash)`, which starts only if the uid isn't running or its hash changed, and stops-then-starts on change — never a second poller for the same uid. Any other status, or a uid no longer present in the collection, calls `manager.stop(uid)`. Volatile fields (`lastSeenAt`, `entriesThisMonth`, `createdAt`) are never part of the hash, so activity/quota writes (later work) don't bounce the worker. `WorkerManager` takes an injectable process launcher (defaults to `subprocess.Popen`) so tests never spawn a real interpreter.

**Firestore wiring** (`runner/firestore_listener.py`, `runner/main.py`) is a thin, untested-by-smoke layer: one `firebase_admin` app, one `on_snapshot` listener on `tenants`, each callback calling `reconcile()`. Profile selection follows the SDK's own convention, nothing invented: `FIRESTORE_EMULATOR_HOST` set → `local` (Firebase Emulator Suite, any `demo-*` project id, no credentials); unset with `GOOGLE_APPLICATION_CREDENTIALS` pointing at a service account → `dev` (an existing dedicated, non-production Firebase project, per spec's Environments section). Documented, never defaulted to a production project.

**Docker/local-dev wiring stays separate from self-host.** A new `runner/Dockerfile` and root `docker-compose.runner.yml` (not `docker-compose.yml`, which self-host users run unchanged) build a runner image that has `hisab/` (to exec the subprocess) plus `runner/`'s own extra dependencies (`firebase-admin`, kept out of the base `requirements.txt`/image so self-host stays lean). `pynacl` is the one new base dependency (`requirements.txt`), since the smoke fixture needs it too. `firebase.json` (already serving `landing/out`) gains `emulators.firestore`/`emulators.auth` port blocks; a deny-by-default `firestore.rules` keeps the emulator bootable without granting anything — #7 replaces it with real owner-scoped rules for the portal's client writes.

**Invariants kept.** Six tools, strict-check append, entry numbers, offset-after-batch: untouched — the runner never imports `hisab.tools`/`hisab.ledger` directly, it only shells out to the existing `hisab.loop` entrypoint. Three-languages-or-none: no new user-facing string ships in this plan (the pending mute is silent by design; #7 owns the pending reminder copy). Privacy: no production project id, real service-account key, personal ledger, or payment provider anywhere in this plan's files; `runner/config.yaml`, `runner-data/`, `*.env`, and any real service-account JSON are gitignored.

## Risks

- **Firestore snapshot listener semantics under real network conditions** (reconnect after a dropped emulator, ordering of rapid successive writes) are not exercised by the no-network smoke suite. Mitigated by keeping `reconcile()` pure and idempotent regardless of call order or duplicate calls — the manual local-emulator run in Phase 5 is the seam that actually proves the listener, not smoke.
- **`pynacl` becomes a base dependency.** Self-host users who never touch hosted mode now install one small extra wheel. Accepted — it is the only way to unit-test the crypto contract without network, and it is a well-established, small library.
- **A retired runner keypair strands any tenant whose ciphertext was sealed under it.** Acceptable for this MVP (local/dev only, per spec's Environments section); documented in `runner/README.md` as a manual-resubmit step, not silently swallowed.
- **Subprocess lifecycle on host restart.** This plan does not add persistence of `WorkerManager` state across a runner restart — on restart, the next Firestore snapshot naturally re-reconciles every tenant from scratch (idempotent by design), so this is a non-issue rather than a gap, but it's worth stating: there is no separate "recovery" code path because none is needed.
