# feat: Connect a phone-authenticated portal user to an agent          ✅ COMPLETED — started 2026-09-12, shipped 2026-09-13

## Problem

[#7](https://github.com/mhmzdev/hisab-whatsapp/issues/7) is the seam where the two built halves of Hosted Hisab meet. The backend exists: the runner reconciles Firestore tenants into isolated workers ([#4](https://github.com/mhmzdev/hisab-whatsapp/issues/4)), pending workers stay silent, `export-ledger` ships a ledger ZIP ([#8](https://github.com/mhmzdev/hisab-whatsapp/issues/8)), the model-call quota enforces ([#6](https://github.com/mhmzdev/hisab-whatsapp/issues/6)), and the transport respects the platform's rate limits ([#17](https://github.com/mhmzdev/hisab-whatsapp/issues/17)). The UI exists: six portal screens built from the Hisab Portal design. **Nothing connects them.** `firestore.rules` is deny-by-default, the portal's nonce is a display constant in `landing/content/mock.js`, and no browser code has ever written a tenant document.

Blockers [#3](https://github.com/mhmzdev/hisab-whatsapp/issues/3) and [#4](https://github.com/mhmzdev/hisab-whatsapp/issues/4) are both closed. [#5](https://github.com/mhmzdev/hisab-whatsapp/issues/5) is blocked on this.

Contract: [spec 001](../../specs/001-hosted-portal.md) ("Trust and authentication", "Verification and language"), [brainstorm](../../brainstorm/hosted-portal.md). Eight design forks were settled in a `/grill-me` pass before this plan; each is recorded as a decision below, not re-litigated.

## Approach

**The runner matches the nonce — the worker never learns what Firebase is.** A muted worker already records every pending inbound to `messages.jsonl` and the sender to `creator.json` (`hisab/loop.py:170-176`; the comment there already says "a later feature reads it for the verify command"). The runner — which alone holds the Firestore client, by the dependency split decided in #4 — reads those two files, finds an exact case-insensitive `verify <nonce>`, and writes `status: "connected"` plus `creatorId`. Its existing idempotent `reconcile()` (`runner/reconcile.py:36-54`) then restarts that tenant's worker without the `pending` flag, because `pending` is part of the state hash at `runner/reconcile.py:28`. No new coupling, no second path to "connected", and `hisab/` gains no Firebase dependency.

**The browser can never write `status` or `creatorId`.** Those two fields decide *whether a worker runs* and *whose agent it is*, and `reconcile()` trusts `status` at `runner/reconcile.py:40`. A client that can set `status: "connected"` skips verification entirely. `firestore.rules` therefore allows a signed-in user to create and update only `agentName`, `keyCiphertext`, `nonce`, `nonceExpiresAt` and `createdAt` at `tenants/{uid}` where `uid == request.auth.uid`, and denies every other field to every client. The runner assigns `status: "pending"` itself, the first time it sees a document carrying a decryptable `keyCiphertext`, so "pending" means "the runner accepted this", not "the client asserted it". The Admin SDK bypasses rules, so the runner is unaffected.

**Verification latency is a 2-second poll, not an event.** Firestore pushes document changes, but the `verify` message lands on disk in the worker's state dir, which Firestore knows nothing about. `runner/main.py:22-23` currently idles in a `while not stop: time.sleep(1)` loop; that loop gains a check over *pending tenants only* every 2s. Connected and revoked tenants are skipped, so it is a handful of small files. No filesystem-watch dependency.

**Nonce lifecycle:** generated in the browser, 6 digits, written with a 10-minute `nonceExpiresAt`. On expiry the runner simply stops matching it; the portal's existing "Get a new code" button (built by the design pass) writes a fresh nonce and expiry. Nothing is torn down — the tenant stays pending and the worker keeps running muted, so a user who walked away to find their phone is not punished.

**The pending agent does reply**, resolving a live contradiction: spec 001 says a pending tenant receives "a short language-neutral reminder", while the shipped mute at `hisab/loop.py:171-176` sends nothing at all. Silence means someone who pastes a key, gets distracted, and later texts "2500 chai" sees no response and concludes the product is broken. The reminder is language-neutral (the user has not chosen a language — setup runs only after verification), sent only after the user messages first (the platform forbids an unsolicited first send anyway), and throttled to **once per 10 minutes** so five messages do not produce five nags. It is a send, so it counts against the 12/min limiter from #17; it is **not** a model call, so it costs nothing against the #6 quota.

**The welcome is sent once, by the worker, guarded by a marker file.** After the status flip, reconcile restarts the worker unmuted and it would otherwise sit silent until the user happens to message again. The restarted worker sends the welcome on startup — but workers restart for ordinary reasons (any config change bounces one), so an unguarded "greet on startup" re-greets forever. A `welcomed.json` marker in the tenant's state dir, beside `offset` and `creator.json`, makes it exactly-once across restarts and crashes with no Firestore involvement. The runner does **not** send it: that would be a second piece of code talking to WhatsApp, outside `wa.py` and outside the rate limiter. After the welcome, the existing setup conversation takes over on the next message — language first — with no changes.

**Client-side encryption stays, with `libsodium-wrappers`.** `runner/crypto.py` decrypts with PyNaCl's `SealedBox` (libsodium `crypto_box_seal`). The browser must produce that exact format: a subtly incompatible ciphertext encrypts fine, writes fine, and fails minutes later inside the runner where the user sees "still waiting" forever. Using the identical library on both sides removes that failure class; the ~200KB lands on the portal route, not the landing page. `tweetnacl` + a third-party sealed-box shim is smaller and was rejected for exactly the invisibility of the failure. **A JS-seals → Python-opens round-trip is a mandatory criterion**, not an assumption.

**Permanent auth failures stop; transient ones retry.** `hisab/loop.py:149-152` catches every poll exception, logs, sleeps 5s, and loops forever. A 401 (`error.code 190`) or invalid-token 400 (`code 100`) never becomes valid, so that is an infinite loop burning 12 polls a minute against the #17 limiter. The worker exits with a distinct code on those two; 429, 503, connection resets and hotspot drops retry exactly as today. The runner notices the exit and writes a short `lastError` **code** (not a message) to the tenant document; the portal renders it through `t()` so the three-language rule is not smuggled around by putting English into a database.

**Invariants kept.** Six tools — this adds no tool and no shell; `export-ledger` and `verify` are both intercepted before the model loop. Strict check, entry numbers, undo-by-reply: untouched, no ledger code is modified. Offset-after-batch and message-id dedup: untouched — the pending path at `hisab/loop.py:175` already records ids, so the `verify` message is deduped like any other and never replays. Three languages: every new string lands in `hisab/i18n.py` (worker) or `landing/content/strings.json` (portal) in `en`/`ur`/`roman` in the same phase that introduces it. Privacy: no project id, service-account file, real token, phone number or personal ledger in the repo — fixtures use a `demo-*` emulator project and fake uids.

## Risks

- **A valid key for the wrong agent is undetectable.** Someone pastes a key for agent X and texts agent Y; nothing matches and the nonce expires. Indistinguishable from a user who simply has not texted yet. Accepted: the "Get a new code" path and the `lastError` copy are the only recovery, and the Connect screen's four steps exist to prevent it.
- **Two accounts submitting the same key** would put two pollers on one agent. #17 recognises and logs the resulting 409/`1752041`, but nothing prevents it. Accepted for MVP; a uniqueness constraint on the decrypted token's agent id is future work.
- **reCAPTCHA and real SMS cannot be emulated.** The Auth emulator prints codes to its console, so local dev never sends a text. Real SMS delivery and the reCAPTCHA flow are deploy-time checks that only Phase 5's manual run exercises — and phone auth requires the Blaze plan (spec 001).
- **The 2s poll is a floor on verification latency**, not an event. Acceptable at human timescale; if it ever matters, the worker could write a sentinel file the runner checks first.
- **`libsodium-wrappers` is ~200KB of WASM.** It loads on the portal route only, never on the landing page, and is a deliberate trade for an error class that is otherwise invisible until it reaches the runner.
